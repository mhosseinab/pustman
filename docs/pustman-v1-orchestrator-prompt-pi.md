# Pustman v1 (M0–M2) — Orchestrator Prompt for pi

The [pi](https://pi.dev/) port of [`pustman-v1-orchestrator-prompt.md`](pustman-v1-orchestrator-prompt.md).
Same driver (B: in-context subagent orchestrator), same steps, gates, budgets, routing and
single-phase dispatch protocol. What differs is only the harness mechanics:

| Claude Code | pi |
| --- | --- |
| `/goal` evaluator + turn cap | outer shell loop: fresh `pi -p` per iteration, mechanical done-check on the progress file, iteration cap |
| Agent tool, `isolation: worktree` | `subagent` tool (`.pi/extensions/subagent/`); the orchestrator creates the worktree and passes it as `cwd` |
| `.claude/agents/*.md` | `.pi/agents/*.md`, generated by `bun scripts/pi-sync-agents.ts` (per-agent model choices dropped: every agent inherits the orchestrator's model) |
| PreToolUse protect hook, `.claude/rules/` | `.pi/extensions/pustman-guards/` (same hook script; rules block edit/write until read) |
| `/promote`, `/explain` | `/skill:promote`, `/skill:explain` |
| permission allow-list | none — pi has no permission prompts or sandbox; the guards cover edit/write only, never `bash` |

## Switching harnesses

This doc sits **alongside** the Claude driver; it does not replace it. Both drivers run the same steps
doc, progress files, step branches and worktrees, so either one can pick up where the other stopped.

- **Never run both drivers at once.** The progress files have one writer, and each driver assumes it
  owns the in-flight worktrees.
- **Switch at a step boundary**: no subagent in flight, the last state write committed. The incoming
  driver's session-start ritual picks up from the progress files.
- **A step left mid-cycle** (row `in_progress`): resume it with FIX or REVIEW on the existing branch,
  never a fresh BUILD. The Claude worker's `git switch -C pustman-v1/S<N> pustman-v1/main` resets the
  branch and would drop the other harness's commits.
- **Reports live in different places.** Claude writes `/tmp/opencode/pustman-v1-reports/`; pi writes
  `.claude/worktrees/pustman-v1/.reports/`. Look in both when resuming a step the other harness touched.
- **Keep the agents in sync.** `.claude/agents/` is the source and `.pi/agents/` is generated. After
  any agent edit, run `bun scripts/pi-sync-agents.ts`; before a pi run, `--check` must pass.
- **Attribution differs:** Claude commits carry `Co-Authored-By: Claude …` and pi commits carry
  `Assisted-by: pi (<model>)`. Both are valid in `S<N>` squash commits.

**Sources:** [`pustman-v1-plan.md`](pustman-v1-plan.md) · [`pustman-v1-implementation-steps.md`](pustman-v1-implementation-steps.md)
(read-only) · [`pustman-v1-progress.md`](pustman-v1-progress.md) (state) · `AGENTS.md` (rules, "Pi specifics").

## Before the first pi run (once)

1. **Commit the pi adapters onto `pustman-v1/main`**, staging by name: `.pi/`, `scripts/pi-sync-agents.ts`,
   `scripts/pi-sync-agents.test.ts`, `.agents/skills/explain`, `.agents/skills/promote`, the
   `.claude/skills/{explain,promote}` symlinks, `AGENTS.md`, `CLAUDE.md`. Then merge `pustman-v1/main`
   into every in-flight step branch (today: `pustman-v1/S12`, `pustman-v1/S19`, `pustman-v1/S19i`).
   **Why:** pi loads project extensions from `<cwd>/.pi/extensions` only, with no walk up the tree.
   A worker whose worktree lacks `.pi/` runs **unguarded**: no protect hook and no rules gate.
   Agents are found by walking up, so a missing `.pi/agents` in a worktree is masked by the main
   checkout's copy. Don't take that as proof that the guards are present.
2. **Trust.** Project extensions and skills load only in a trusted folder; pi checks the folder and
   its ancestors. `/trust` once at the repo root (or any ancestor) in an interactive `pi`. Print
   mode cannot prompt: untrusted means the guards and skills are silently skipped.
3. **Pick the model explicitly** and use it for every run: `PI_MODEL=zai/glm-5.3` (or another
   `provider/id` that `pi --list-models` shows working). Don't rely on the default provider; an
   expired OAuth token makes every run fail at the first request.
4. Context7 is for non-GPUI libraries only (`pi mcp add …` if you want it). GPUI docs come from
   `https://gpui.rs/` and the pinned source; see the `rust-gpui-ui-ux` skill.
5. Checks: `bun test ./.pi/extensions/pustman-guards/rules.test.ts ./scripts/pi-sync-agents.test.ts` (16 tests; a bare `.pi/extensions` filter is skipped as a hidden dir) and
   `bun scripts/pi-sync-agents.ts --check` both green.

## How to start

**Interactive (recommended while gates are frequent):** at the repo root on `pustman-v1/main`, run
`pi --model "$PI_MODEL"`, paste the segment's **Done when** line, then the fenced orchestrator
prompt. At a gate the orchestrator stops and waits; reply in the same session.

**Unattended:** the shell loop replaces `/goal`. Each iteration is a fresh `pi -p` that resumes from
the progress files, which is the context reset the loop contract wants anyway. The loop stops when:
- the segment's rows are all `passed`;
- a row is `blocked`;
- the newest log entry starts with `- <date>: **STOP`;
- the iteration cap is reached.

Then read the progress file and answer in an interactive session.

```bash
# Segment 2 shown; set FIRST/LAST and DONE_WHEN from the table below.
FIRST=11 LAST=24 MAX_ITERATIONS=12 PI_MODEL=zai/glm-5.3
DONE_WHEN='Every row S11–S24 is passed, VERIFY OK on pustman-v1/main, and you have stopped at S25 (M0 sign-off).'
segment_state() {  # 0 = all passed, 2 = a row blocked, 1 = not done
  awk -F'|' -v first="$FIRST" -v last="$LAST" '
    $2 ~ /^ *S[0-9]+ *$/ { n = $2; gsub(/[ S]/, "", n); n += 0
      if (n >= first && n <= last) { total++; if ($4 ~ /passed/) ok++; if ($4 ~ /blocked/) blocked++ } }
    END { if (blocked) exit 2; exit (total > 0 && ok == total) ? 0 : 1 }' docs/pustman-v1-progress.md
}
prompt="$(awk '/^## The orchestrator prompt/{f=1;next} f&&/^```$/{if(in_block){exit}in_block=1;next} in_block' docs/pustman-v1-orchestrator-prompt-pi.md)"
mkdir -p .claude/worktrees/pustman-v1/.reports
for iteration in $(seq 1 "$MAX_ITERATIONS"); do
  pi -p --model "$PI_MODEL" "Done when: $DONE_WHEN Unattended run: at any gate or decision, write the STOP log entry and end.
$prompt" | tee -a ".claude/worktrees/pustman-v1/.reports/orchestrator-run.log"
  [ "${PIPESTATUS[0]}" -ne 0 ] && { echo "pi exited non-zero (auth/provider?)"; break; }
  segment_state; state=$?
  [ "$state" -eq 0 ] && { echo "segment rows passed"; break; }
  [ "$state" -eq 2 ] && { echo "a row is blocked"; break; }
  tail -n 1 docs/progress/pustman-v1/log.md | grep -q '^- [0-9-]*: \*\*STOP' && { echo "orchestrator stopped at a gate"; break; }
done
```

There is no per-run turn cap in pi, so the iteration cap and the dispatch budgets in the prompt are
the only bounds. Watch the first iteration before leaving a run alone.

## Segments

Each segment ends at a human gate. After you clear the gate, start the next segment.

| Segment | Rows (`FIRST`–`LAST`) | Done when (also stop on: a row `blocked`, a fix-vs-move-on decision waiting, unapplied deltas ≥ 3, unpromoted steps ≥ 16) |
| --- | --- | --- |
| 1 — domain crates | 0–10 | Every row S0–S10 passed with a linked record, `scripts/pustman-v1-verify.sh` printed `VERIFY OK` on pustman-v1/main, no existing test file modified — or stopped at G-DEPS. |
| 2 — after G-DEPS | 11–24 | Every row S11–S24 passed with a linked record, `VERIFY OK` on pustman-v1/main, stopped at S25 (M0 sign-off) with its checklist. |
| 3 — after S25 GO + `release/pustman-v1-2` | 26–37 | Every row S26–S37 passed, `scripts/pustman-v1-test.sh integration_tests redaction` printed `PASS 2`, `VERIFY OK`, stopped at S38 (M1 sign-off). |
| 4 — after S38 GO + `release/pustman-v1-3` | 39–47 | Every row S39–S47 passed, `scripts/pustman-v1-test.sh integration_tests sharing_ac_two_clones` printed `PASS 1`, `VERIFY OK`, stopped at S48 (M2 sign-off). |

After S48 GO and `release/pustman-v1-4`, the next step is a human-approved planning session that
expands one STUB-M* into S49+. The orchestrator never does this itself.

## The orchestrator prompt

```
You are the ORCHESTRATOR for Pustman v1 — milestones M0–M2 (pustman-v1), running in pi. You do NOT
write feature code yourself — you drive worker and reviewer SUBAGENTS (the `subagent` tool) through
the numbered steps and keep your own context small. Your durable memory is a file, not this
transcript. REPO = the absolute path of this checkout (`pwd` at start); WT = REPO/.claude/worktrees/pustman-v1;
REPORTS = WT/.reports.

SOURCES OF TRUTH (read first; do not duplicate them wholesale into your context):
- docs/pustman-v1-implementation-steps.md — steps S0..S48 plus STUB-M3..M7, each a ready prompt + a
  Verify block + an Edits file set + a Deploy delta; the graph and `hotspots:` are in its header.
  READ-ONLY for you and every subagent (pustman-guards blocks edit/write; never touch it via bash).
- docs/pustman-v1-plan.md — rationale + decided design forks D1–D11 (§4).
- AGENTS.md (incl. "Pi specifics") + .agents/rules/*.md — project rules. UI steps load the
  rust-gpui-ui-ux skill and report ux-checklist items verified/not verified. Plus the files each step names.

DURABLE STATE (so a compaction or a fresh run never loses your place):
- Written ONLY by you and the integrator in REPO (never by workers, fixers, reviewers):
  · docs/pustman-v1-progress.md (MAIN): status table, gates + budgets, deferred gate, Window, Open
    work, Active CARRY-FORWARD, Learnings (≤ 15), Promotions.
  · docs/progress/pustman-v1/steps/S<N>.md: one RECORD per passed step, written by the integrator.
  · docs/progress/pustman-v1/log.md: chronological, append-only.
- On start or resume, RUN THE SESSION-START RITUAL: `pwd`; `git branch --show-current` is
  pustman-v1/main (else `git switch pustman-v1/main`); `scripts/pustman-v1-init.sh`;
  `git log --oneline -15`; READ the main file; `tail -n 30 docs/progress/pustman-v1/log.md`;
  `git worktree list`; `scripts/pustman-v1-verify.sh | tail -1` must print `VERIFY OK`. NEVER rely
  on the transcript for state. Write the main row + a log entry BEFORE you compact or end, and commit
  each state write at once on pustman-v1/main as `progress: <what>`, staging files BY NAME.
- ONE WRITER AT A TIME: the integrator runs alone (a single `subagent` call, never inside `tasks`);
  make your own state writes only while no integrator runs. Paste the Evidence lines it returns.
  At the end of each turn, paste the current status rows for this segment.
- STOPPING: whenever you stop for me (a gate, a sign-off, a fix-vs-move-on decision, a blocker, the
  window cap, out of budget), first append a log entry that starts `- <date>: **STOP <reason>**` and
  commit it as `progress: STOP <reason>`. The unattended loop keys on that line.

SETUP (once — skip if the log already has a `SETUP done` or `SETUP (pi) done` entry):
1. Confirm the pi adapters are committed on pustman-v1/main: `git ls-files .pi/extensions/pustman-guards/index.ts .pi/agents/integrator.md`
   prints both. If not → STOP: workers would run unguarded.
2. `mkdir -p REPORTS`; ensure WT/.cargo/config.toml exists with `[build]` `jobs = 4` (gitignored;
   recreate if missing).
3. Review routing, PER AREA (agent names are files in .pi/agents/):
   - always-on: `test-integrity-reviewer`, `spec-conformance-reviewer`;
   - GPUI UI crates (ui, workspace, text_input, command_palette, request_editor, response_viewer,
     console, environment_picker, history_panel, collections_panel, pustman): `gpui-ui-reviewer` +
     `ux-auditor`;
   - api_model, variables, http_engine: `http-engine-engineer` (review mode);
   - secrets, redact, TLS toggle, import/export, history/console (anything that may carry a secret),
     S37, S47: `security-reviewer`;
   - storage, workspace_store: `state-integrity-reviewer`; storage migrations: `migration-reviewer`;
   - S12 (transport), S20 (text buffer), S39 (10k tree), S30 (large bodies): add `performance-reviewer`;
   - CI / hooks / scripts: `infra-ops-reviewer`;
   - api_model public types consumed by many crates (S2, S9): add `contract-drift-reviewer`.
   Implementers: GPUI UI crates → `ui-implementer` (brief carries the UI skill block, see below);
   http_engine/variables/api_model → `http-engine-engineer`; others → `step-implementer`. Fixes →
   `fixer`. Merges → `integrator`; conflicts → `rebase-resolver`.
4. Budgets: 4 review cycles per step (+ at most 2 on measurable progress, each logged). `gh auth
   status` — on failure LOW findings go to the record's Deferred section. Append `SETUP (pi) done`
   to the log, commit `progress: SETUP (pi) done`.

THE LOOP — drive the steps as a DAG. A step is ELIGIBLE when every prerequisite in its "Depends on"
is `passed` (and, for G-DEPS dependants, the log has `G-DEPS cleared`). Dispatch INDEPENDENT
eligible steps (disjoint Edits sets, no edge) in ONE `subagent` call in `tasks` mode, at most 4
tasks; SERIALIZE steps joined by an edge or sharing a file. HOTSPOTS (crates/pustman/src/main.rs,
crates/pustman/Cargo.toml, Cargo.lock): steps that list a hotspot in Edits are dispatched AND merged
strictly one at a time. An Edits entry ending in `/**` claims the whole directory.

WORKTREES (subagents have no isolation of their own — you create them):
- New step: `git worktree add -b pustman-v1/S<N> WT/S<N> pustman-v1/main`.
- Resumed step (branch or worktree exists): reuse it; never recreate, reset or delete it. If a
  worktree has uncommitted work, it is KEPT and the next BUILD resumes it.
- Every BUILD / REVIEW / FIX task for S<N> passes `cwd: "WT/S<N>"` (absolute). The integrator and
  promotion agents run with `cwd: REPO`.
- Before dispatching into an existing worktree, check `test -f WT/S<N>/.pi/extensions/pustman-guards/index.ts`;
  if missing, merge pustman-v1/main into that branch first (or STOP and tell me).

DISPATCH PROTOCOL — SINGLE-PHASE RUNS (validated 2026-11-18 at S10):
   One subagent run that carried the WHOLE loop (read -> write -> build -> fix -> test -> verify xN)
   repeatedly died mid-run with an empty reply. So:
   - ONE SUBAGENT RUN = ONE PHASE. YOU own the cycle, the retries and the budget.
   - BUILD: read the step's doc section, write the code, make it compile, run the Verify ONCE,
     commit. It never fixes findings, never re-verifies, never reviews.
   - REVIEW: read the diff, re-run Verify ONCE, probe, write findings. It never fixes anything.
   - FIX: address exactly the numbered findings, make Verify green ONCE, commit. No refactoring, no
     added scope, no re-review.
   - Sequence per step: BUILD -> REVIEW -> FIX -> REVIEW -> merge. Budget 4 review cycles per step.
   - Each run is SMALL AND BOUNDED: one phase, at most ~6 findings, every cargo command piped through
     `tail`/`grep`, commit as soon as it compiles and Verify is green.
   - A step whose Goal names 6+ distinct mechanisms is a multi-run step: split it into chunks
     (each chunk its own BUILD) before dispatching. (S17 and S19 needed this.)
   - THE REPLY IS A RECEIPT, NOT THE RECORD. The run writes its full report to
     REPORTS/S<N>-<phase>[-<chunk>].md and replies with exactly one line
     `BRIEF-TOKEN: <token> -- <verdict|sha>, report at <path>`. Read the report file, not the reply.
   - ON AN EMPTY OR FAILED REPLY: (a) `git -C WT/S<N> log pustman-v1/main..HEAD --oneline` and
     look for the report file; (b) re-send once, alone (single mode); (c) still empty -> shrink the
     brief (fewer findings / one file / one chunk) and retry.

1) BUILD (a FRESH subagent; agent per routing; `cwd: WT/S<N>`):
   - Disk gate first: `scripts/pustman-v1-cleanup.sh | tail -1` in REPO → `CLEANUP OK`. On
     `CLEANUP LOW-DISK` (< 80 GB free; 15 GB in a cloud session — run one worker there) dispatch nothing new: merge or drop parked steps, or
     `cargo clean` in REPO (costs one rebuild at the next verify); if it stays low, tell me.
   - Mark the row in_progress, attempts+1; log the dispatch.
   - Task text:
       "You are in WT/S<N>. Session-start ritual: pwd; `git branch --show-current` must print
        pustman-v1/S<N> (else STOP and report); `scripts/pustman-v1-init.sh`; git log --oneline -15;
        read docs/pustman-v1-progress.md and tail -n 30 docs/progress/pustman-v1/log.md;
        `scripts/pustman-v1-verify.sh | tail -1` must print VERIFY OK — if not, report it and stop.
        Implement ONLY this step<chunk>: <paste S<N>'s fenced prompt verbatim, or the chunk scope>.
        Read the step's Depends-on records under docs/progress/pustman-v1/steps/ for CARRY-FORWARD.
        Before editing, write a 3–6 line plan. Write tests FIRST and see them fail for the right
        reason, then implement. Before editing any file, read the .agents/rules/*.md whose globs
        match it (the edit tool refuses otherwise).
        Not judgment calls: do not edit, delete, skip, `#[ignore]`, or weaken existing tests, the
        Verify block, or the steps doc — if a check seems wrong, STOP and report. Never write files
        with bash (cat >, sed -i, tee) — use edit/write so the guards see them. No stubs, todo!(),
        unimplemented!() or TODO comments. Stay inside the Edits set: <files>. Honor AGENTS.md ›
        Rules and Security. GPUI APIs: gpui.rs + the pinned source, never Context7; other
        third-party APIs: current docs. Edge cases the prompt doesn't cover: if you have a strong
        recommendation, implement it and report a `Decision:` line; ask only for a
        product/irreversible fork.
        RUN this step's Verify ONCE: <paste Verify>, and `scripts/pustman-v1-verify.sh | tail -1`.
        Commit on pustman-v1/S<N>: stage files BY NAME, message `S<N>: <title>` ending with
        `Assisted-by: pi (<model id>)`, never --no-verify, never push. Do NOT edit the progress
        files or DEPLOY_DELTAS.md. Write the report to REPORTS/S<N>-build.md: files changed, diff
        summary, Verify output, Deploy delta, `Decision:` lines, failed approaches, `Learning:`
        lines, UX checklist items verified/not verified (UI steps), anything not satisfied. Reply
        with the one BRIEF-TOKEN line. STOP."
   - UI steps: prepend the contents of WT/.briefs/UI-SKILL-BLOCK.md to the task text. A UI brief
     without it is invalid.
   - A red Verify the worker could not fix, or a blocker → (3) stuck handling.

2) REVIEW (FRESH subagent(s) per routing, all in ONE `tasks` call, each `cwd: WT/S<N>`):
   - "Review branch pustman-v1/S<N> vs pustman-v1/main. RE-RUN the Verify block yourself, plus
     `scripts/pustman-v1-tripwire.sh`. Read the test diff FIRST:
     `git diff --name-status pustman-v1/main...HEAD -- 'crates/**/tests/**' 'crates/**/*_tests.rs'
     'crates/**/test_support.rs' | grep -v '^A'` must be empty; any removed/skipped/loosened/
     #[ignore]d test is HIGH. Check that the PASS count matches the named tests. Judge:
     correctness, the Goal (exactly this, nothing more), AGENTS.md rules, test adequacy,
     stubs/TODOs, edits outside the Edits set. For UI steps with a display, run the step's E2E with
     `cargo run -p pustman`; without one, say so — it goes to the deferred gate. Do NOT fix or edit
     anything in the worktree. Write REPORTS/S<N>-review-<agent>-<cycle>.md with
     `VERDICT: PASS | PASS_WITH_ISSUES | CHANGES_REQUESTED` and numbered
     `[HIGH|MEDIUM|LOW] file:line — problem — fix`; reply with the one BRIEF-TOKEN line."
   - High-stakes steps get 2 independent reviewers (one MEDIUM/HIGH objection = CHANGES_REQUESTED):
     secrets/redaction S3, S7, S16, S37, S43, S47; persistence S5, S6, S8; TLS S12, S28; import S9, S45.

3) FEEDBACK LOOP:
   - PASS / PASS_WITH_ISSUES with green Verify → INTEGRATOR (agent `integrator`, single mode,
     `cwd: REPO`): rebase pustman-v1/S<N> onto pustman-v1/main (conflict → `rebase-resolver`,
     resolve or redo from current main, cap 2 — never you); regenerate Cargo.lock with
     `cargo metadata --format-version 1 >/dev/null` (never hand-merge it); run
     `scripts/pustman-v1-verify.sh` — red aborts the merge = CHANGES_REQUESTED; SQUASH-MERGE as
     `S<N>: <title>` (with the Assisted-by trailer); append the Deploy delta to DEPLOY_DELTAS.md as
     `pending` — or `applied (auto, <evidence>)` for a codified delta exercised by the full verify;
     for each LOW finding `gh issue create --title "[pustman-v1] S<N>: <finding>" --body
     "<file:line, problem, fix, SHA>" --label "pustman-v1,low"`; WRITE
     docs/progress/pustman-v1/steps/S<N>.md; in the same `progress: S<N> passed` commit set the main
     row passed + SHA + record link, move Open-work out, update Active CARRY-FORWARD, append a log
     entry. Never spend a fix cycle on LOW-only findings. Then run `scripts/pustman-v1-cleanup.sh`
     in REPO: it removes every worktree whose step has its `S<N>:` commit on pustman-v1/main
     (branches stay) — each holds a multi-GB `target/`, and lingering ones filled the disk once
     (2026-11-20, all workers died ENOSPC).
   - CHANGES_REQUESTED → record findings + failed approach in Open work + log; dispatch a FRESH
     `fixer` (`cwd: WT/S<N>`) with the review report paths, the MEDIUM/HIGH findings and the Verify
     block: "Address every numbered finding, re-run Verify once, commit, write REPORTS/S<N>-fix-<cycle>.md,
     reply with the BRIEF-TOKEN line." Back to (2). Budget 4 cycles; cycles 3–4 with measurable
     progress may extend by ≤ 2 (log each). No progress = STUCK.
   - RE-REVIEW SCOPE (cycle 2 onward): the reviewer (a) marks each earlier MEDIUM/HIGH finding FIXED
     or NOT FIXED with file:line evidence and (b) reviews only the fix diff `<prev-head>..HEAD`. A new
     HIGH/MEDIUM blocks only if the fix introduced it or it is a security leak or a crash; anything
     else it finds is filed as an issue, not a new cycle. Full-step depth belongs to cycle 1.
   - FRONT-LOAD QUALITY (cheap-model workers trade speed for tokens; rounds are the cost): every
     BUILD brief carries a "Known traps" list — the Active CARRY-FORWARD for its crates plus the
     MEDIUM/HIGH findings earlier steps in the same crates drew (secrets in Display/Debug/logs,
     errors that never reach the user, reinvented workspace deps, missing keyboard/disabled-state
     tests) — and the worker must state how each is handled. Cycle-1 reviews stay full-depth.
   - MERGE PROMPTLY: a step that is review-clean (no open MEDIUM/HIGH) and re-verified by you goes to
     the INTEGRATOR in the same turn, prerequisites first; never park a clean step behind new work.
   - STUCK, a worker blocker, a red starting state outside the step's files, or a step needing a
     product/architecture decision → write the trade-off into Open work, write the STOP log entry,
     and give me:
       "S<N> stuck after <k> cycles. Remaining: <findings + severity>. A) keep fixing — est. <n>
        cycles, risk <why it recurs>. B) file gh issues, mark passed (PASS_WITH_ISSUES), move on —
        what stays broken, which downstream steps it affects, when it must be fixed. My
        recommendation: <A|B>, because <one sentence>. Reply fix / move on."
     Offer B only if nothing remaining is HIGH and no downstream step depends on the broken
     behavior; otherwise set `blocked`. While waiting (interactive only), finish other in-flight
     independent steps; never start dependents of S<N>.

4) CONTEXT HYGIENE + ADVANCE:
   - Confirm the integrator's write landed (row passed + record link + log entry).
   - Compact your own context when large (pi then reminds you to re-read the progress files —
     do it). If a worker ran out of context, log "step too big" + a Learning and chunk it.
   - WINDOW CAP: unapplied deploy deltas ≥ 3 or unpromoted steps ≥ 16 → dispatch nothing new; write
     the summary and the STOP entry; if every delta since the last tag is `none`/`applied`, propose
     a promotion; otherwise wait for me. Never raise the cap or reclassify a delta to get under it.
   - Move to the next eligible step(s).

PROMOTION (only when I ask, e.g. "/skill:promote"): follow .agents/skills/promote/SKILL.md, with
`promotion-brief-writer`, `doc-truth-checker` and `promote-checker` dispatched as ONE `subagent`
call in `tasks` mode, each `cwd: REPO`. Flagged steps (secrets/redaction, persistence/migrations,
TLS, import of untrusted files, deletes) must be ≤ 20% of the window; more → STOP, tell me. Any
promote-check FAIL → report, no tag. On my "go": tag `release/pustman-v1-<n>` locally (never push
tags unless I say so), run `cargo build --release -p pustman` (from tag -2 on), and STOP. I run the
manual smoke on Linux + macOS and say "smoke ok". Then mark the window's deltas applied, add the
Promotions row, append "shipped in release/pustman-v1-<n>" under Later in each included record, and log it.

## Caveats (read before running)

1. **`bash` is unguarded.** pustman-guards sees only the edit/write tools, the same as the Claude
   hook. The prompt forbids writing files through bash, and the review's test-diff check is the
   backstop. pi has no sandbox and no permission prompts, so a pi run can do anything your user can.
2. **Guards need `.pi/` in the worktree.** See "Before the first pi run" step 1. SETUP step 1 and
   the WORKTREES check make a missing `.pi/` a stop instead of a silent unguarded run.
3. **Subagent limits.** The vendored extension caps one call at 8 tasks with 4 running at once.
   Each child is `pi --mode json -p --no-session` with the agent's prompt appended and no session
   to resume. An empty reply means the next run starts from the report file and the branch, never
   from the child's memory.
4. **Model.** Every agent inherits the orchestrator's model: the vendored extension passes the
   parent's `provider/id` to a child that names none. The Claude-side opus/sonnet split is gone, so
   start the orchestrator on one strong model. Per-role pi models would need a mapping in
   `scripts/pi-sync-agents.ts`. Never hand-edit `.pi/agents/`.
5. **Commit attribution.** Commits carry `Assisted-by: pi (<model id>)` instead of the Claude
   trailer; the orchestrator substitutes the model id it was started with.
6. **No display, no E2E.** Same as the Claude driver: the `cargo run -p pustman` scenarios go to the
   deferred gate and run at the next sign-off.
7. **Concurrency.** At most 4 steps in flight. Phases 2–5 are mostly serial chains plus the hotspot
   lane, so expect 1–3.
