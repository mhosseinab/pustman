## Goal
A single pure function masks secrets in text, headers and URLs. History, Console and export all
depend on it (D8) — a hole here leaks secrets everywhere downstream.

## What shipped
`api_model::redact` — `SecretValues` (a set of literal secrets; empty and <4-char values ignored,
and values containing the mask character `•` refused and COUNTED by `refused_count()`),
`redact_text` (occurrence-span merge → `••••••`), `redact_headers` (the 14 credential headers masked
whole on their visible-ASCII name, raw OR redacted; names run through `redact_text` too),
`redact_url` (fixed-point loop over: registered-secret occurrences ∪ userinfo password regions
masked as ONE span union, then decode-aware whole-component masking for path/fragment/query
names/query values/userinfo/host, then `redact_text`, then a whole-decoded-URL pass).

## Findings history (6 rounds)
- **R1** lexicographic replacement split overlapping secrets (near-whole leak); percent-encoded
  secrets survived outside query values; userinfo username unmasked; scheme-relative/schemeless
  authority leaked; secrets in header NAMES survived; whitespace-padded names defeated the
  always-mask; the credential list was only 4 headers; idempotence broke on mask-substring secrets.
- **R2** schemeless URL with a later `://` leaked the password; a secret containing `/ & = ? #` or
  `+` and partly encoded survived (7 shapes); invisible Unicode padding (`\u{200b}` etc.) defeated
  the name match; `ab••` silently dropped; a percent-encoded host secret survived.
- **R3** **REGRESSION** from the R2 fix: malformed-scheme URLs (`://`, `1://`, `my_app://`) stopped
  masking the password; `redact_headers` decided the credential verdict on the UN-redacted name so
  the FIRST application leaked an unknown credential value; `SecretValues::insert` dropped `•`
  values silently (fail-open).
- **R4** **REGRESSION** from the R3 fix: running `redact_text` first consumed the `@` of a secret
  straddling it, so `mask_userinfo` never fired and the password prefix leaked. Nested
  schemeless/scheme-relative URLs still leaked. Termination proof wrong.
- **R5** **REGRESSION** from the R4 fix: the "drop nested regions" filter dropped the LARGER of two
  overlapping regions, so a password with a second `@` (`p@ssw0rd`, Azure-SQL `user@tenant:pass`)
  leaked its tail.
- **R6** PASS_WITH_ISSUES ×2 — the HIGH verifiably closed, all prior shapes hold, fuzz clean.

## Decisions
- **Registered secrets and userinfo are masked as ONE span union against the same input.** Neither
  heuristic may preempt the other: `redact_text` first destroys the `@`, `mask_userinfo` first
  destroys a secret containing its own `://`. A username prefix survives only by falling in a gap,
  so a secret touching it masks it too.
- **`SecretValues` refuses any value containing the mask character `•`** — and this is CORRECT,
  not over-cautious. Both round-3 reviewers ran the mutant: `redact_text("abab••", {ab••})` →
  `once="ab••••••"`, `twice="••••••••••"`. `ab••` re-matches at a preserved-text/mask junction.
  The blanket rule is what preserves idempotence; a narrower rule cannot. **What is NOT acceptable
  is the silence** — hence `insert -> bool` + `refused_count()`.
- **An empty password is not expanded to the mask** (`user:@h/x` unchanged) — it has nothing to
  hide, and inserting bullets only asserts a password exists.
- **Email-shaped over-masking is the accepted safe direction** (`?email=bob@example.com` → masked;
  `see mailto:bob@example.com` masks because `is_opaque_scheme` compares `see mailto`). The
  ambiguity is undecidable — `bob@example.com` is byte-identical to the deliberately masked
  username-only PAT shape — so "fixing" the email case necessarily unmasks PAT-shaped usernames.
  Must be recorded in code: issue #11.
- **A userinfo runs to the LAST `@`** — a password may hold one (`p@ssw0rd`) and a username may be
  `user@tenant` (Azure-SQL). Overlapping regions are MERGED, never dropped.
- **First-`:` split** for the password (not last-`:`) — masks strictly more.

## Learnings (the important ones)
- **A fix in a security boundary is only credible once its test is shown to FAIL for the right
  reason.** Every round here used a mutant or old-vs-new comparison; each of the 5 regressions was
  caught that way. This is the expected standard for this loop.
- **Never reason about an idempotence or fixed-point claim — run the mutant.** The orchestrator
  argued `ab••` was idempotent-safe and was wrong; two reviewers refuted it with one probe.
- **A heuristic that preprocesses text can destroy the evidence a literal pass needs.** Four of the
  five regressions were exactly this shape: each new masking pass consumed characters another pass
  needed. Compute all masks against the SAME input and merge the spans.
- **`is_opaque_scheme` compares the whole prefix**, so `see mailto` is not `mailto` — position
  matters and prose context silently changes behavior.
- A dispatched subagent can return an EMPTY reply with no commit — always check
  `git log pustman-v1/main..pustman-v1/S<N>` before treating a return as progress. S3's fixer
  failed 8 times across 4 prompt styles and 2 worktree locations while every reviewer succeeded.
