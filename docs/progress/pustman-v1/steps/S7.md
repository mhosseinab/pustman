## Findings
1. **[MEDIUM] `keyring_store.rs` (get)** — `KeyringStore::get` returned `Ok(SecretValue(""))` for a
   keychain entry written *outside* `SecretStore::set` (user edits it empty in macOS Keychain Access
   / Windows Credential Manager / `secret-tool`, another tool, a prior buggy build). This broke the
   crate invariant ("get returns a non-empty value or NotFound") and the store-consistency claim,
   and re-opened exactly the hole `check_value` closes on `set`: a secret resolving to an empty
   string sent silently, which REQ-VAR-SHARE-02 forbids. **Both reviewers found it independently.**
   **Fixed** in `d36b296`: shared `checked_stored_value` helper applied in BOTH stores' `get`,
   new test `memory_store_get_rejects_an_empty_stored_entry` (injects an empty entry straight into
   the map — the Keychain-Access-edited scenario), invariant docs updated. Re-review: PASS.
2. [LOW] `keyring_store_tests.rs` — the cleanup comment over-claimed: `?` on `get` early-returned
   before `delete`, so a locked keychain could leave an entry behind. **Fixed**: `Cleanup` Drop
   guard deletes on every exit path (no `let _ =` — matched with named error), comment narrowed.
3. [LOW] `secrets.rs:30,47` — `[`MemorySecretStore`]` intra-doc links unresolved in the default
   build (the type exists only under `test-support`); `cargo doc` warned twice. **Fixed**: plain
   backticks.

## Decisions (worker; re-verified by both reviewers)
- **Debug hides values**: `SecretValue(String)` has hand-written `Debug` *and* `Display`, both
  printing `<redacted>`; `MemorySecretStore`'s `Debug` is `MemorySecretStore(<redacted>)`.
  `debug_output_hides_value` proves it with a sentinel (`token-REDACTED-example`): asserts
  non-containment in `{:?}`/`{}` of `SecretValue` **and** in `{:?}` of a store holding it. No custom
  `Drop` (workspace denies `unsafe_code`, so no byte-zeroing) — a destructor that formats the value
  is the leak the type prevents; documented on the type.
- **`test-support` feature is `[]`** — keyring/thiserror publish no `test-support` to forward to
  (rule satisfied vacuously; commented in the manifest). It gates the export via
  `#[cfg(any(test, feature = "test-support"))]` on module + re-export, so `cargo test -p secrets`
  compiles it through `cfg(test)` while downstream dev-deps opt in. Verified both ways.
- **`SecretKey` rendering is injective**: service `SecretKey::SERVICE = "pustman"`, account
  `"<workspace_id>/<scope_id>/<variable_key>"`, defined once in `Display`, exposed as `account()`.
  `new()` validates: non-empty, NUL-free; `workspace_id`/`scope_id` may not contain `/` (the
  separator — a slash there would let two keys render as one account); `variable_key` **may**
  contain `/` (`api/v2/token`) and stays unambiguous because the two id components are
  separator-free. The account is documented as a rendering never parsed back.
- **`SecretError` never carries values**: `NotFound{key}`, `InvalidKey{reason}`,
  `InvalidValue{key}`, `BackendUnavailable{reason}`, `UnusableSecret{key}`. **Critically,
  `keyring_core::Error::BadEncoding(Vec<u8>)`/`BadDataFormat(Vec<u8>,_)` literally carry the stored
  bytes** (and their `Debug` would print them), so `map_error` matches those first and DROPS the
  error → `UnusableSecret`; only platform-safe variants are stringified, `Ambiguous` and unknown
  (`#[non_exhaustive]`) get fixed text.
- **Empty values refused on write AND read** (`check_value`/`checked_stored_value` shared helper):
  an empty secret is indistinguishable from unset and would violate "never an empty string sent
  silently". `delete` is idempotent (keyring `NoEntry` → `Ok`).

## Learnings
- `keyring` 4.x ≠ 3.x: `Entry` lives behind the default `v1` feature; errors come from
  `keyring-core`. Read the pinned crate source, not "latest" docs, when a workspace pin exists.
- **`keyring_core::Error` carries secret bytes** on `BadEncoding`/`BadDataFormat` (its `Debug`
  prints them) — any wrapper in front of it must DROP those variants, never forward them.
- `clippy::default_constructed_unit_structs` is fatal under `-D warnings` (use `Self`, not
  `Self::default()`, in a unit struct's `new`).
- A `test result: ok.` **doc-test line counts** toward `pustman-v1-test.sh`'s `PASS <n>` — no
  fenced Rust examples in doc comments when the Verify pins the count.
- Windows Credential Manager compares target names case-insensitively — two variable keys differing
  only in case could collide there. Worth one manual check at Windows sign-off alongside
  `live_keyring_roundtrip` (not provable on this Linux host).
