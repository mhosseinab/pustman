## What shipped
`WorkspaceWatcher::watch(root)` + `FsChange{ItemAdded, ItemChanged, ItemRemoved, Problem, Rescan}`
over `notify`, debounced 100 ms, `.git/` and dot-entries ignored, `InvalidJson` positions kept
verbatim (S5's contract). `record_own_write` / `record_own_rename` suppress our own writes.

## Findings history — the watcher was missing the events it exists for
- **R1 (3 HIGH + 3 MEDIUM):** own-write suppression was a permanent ABA hole (hash stored forever,
  never consumed — any later external write with the same bytes was swallowed); directories and the
  root were dropped silently, so the **git-pull shape (mkdir + immediate writes) lost every file**;
  `record_own_write` covered one path but `save_item`'s rename touches two, so the old-file delete
  leaked as `ItemRemoved` and a consumer dropped the item it just renamed; an id change at a known
  path reported only the new id; within-batch lexicographic order could invert a rename's legs.
- **R2 (1 HIGH):** the `Rescan` mitigation reached only *container* renames — a leaf rename produces
  no directory event, and `record_own_write` on the old path cannot help (the bytes are gone).
- **R3:** the fix was correct but the assertion was not discriminating (the `expect_timeout` let the
  rename's own Remove consume the marker first). Pinned with a coalesced-window test and proved by
  mutation: removing the `exists()` guard makes it fail.

## Decisions
- **Own writes are one-shot and typed.** `OwnWrites` holds `Option<u64>`: `Some(hash)` is bytes we
  wrote (matched by content), `None` is a path we deleted (the old leg of a rename). Both are
  consumed on match. The `None` arm matches **only while the path is genuinely absent** — a stale
  or coalesced marker must never eat a genuine external change at that path.
- **`record_own_rename(root, previous, saved)`** is the API for a rename; a caller that only calls
  `record_own_write` on the returned path will leak the old leg. Documented on the method.
- **Directories and the root emit `Rescan`.** notify reports directory creates and renames, and a
  git-pull writes children before their watch is armed; dropping those loses the files outright.
- **Removals are processed before additions** in a batch, so a rename's two legs cannot invert.
- **The new id at a known path arrives as `ItemAdded`** — it is unseen even though the path is
  known, and a consumer that only inserts on `ItemAdded` would otherwise drop it.

## Learnings
- A mitigation that covers only one shape of a bug is not a fix. The `Rescan` on directory events
  looked like it closed the rename leak and did not — the probe that separated container renames
  from leaf renames is what caught it.
- A one-shot marker still needs a match criterion. Consuming on sight is not the same as matching:
  without a check that the path is genuinely gone, a stale marker swallows a real change.
- A test that cannot fail is not proof. The first pinned assertion passed with the guard deleted;
  only the coalesced-window shape (rename + external write in the SAME debounce batch) discriminates.

## Deferred
Symlinked item files are followed by the watcher but skipped by `collect_files`/`open`, so a
symlink reports content from outside the root — pre-existing, filed for a follow-up. Unbounded
mpsc channels and an ever-growing map under a stalled consumer.
