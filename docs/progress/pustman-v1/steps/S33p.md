## Why
The S38 headless pre-check found that Manage Cookies never opens (#286). The driver then found the wider gap: `crates/pustman/src/pustman.rs` built `ReqwestTransport` with no cookie jar, and `load_jar`/`save_jar` were never called. The running app neither stored `Set-Cookie`, sent `Cookie`, nor kept cookies across restarts, although cookies are an M1 feature (PRD milestone table).

## What shipped
- `AppCookieJar`: one `Arc<Mutex<CookieJar>>`, passed to `ReqwestTransport::with_cookie_jar`.
- When the store opens (both arms): `load_jar` into the same `Arc`, in place. On failure, a `StartupProblems` entry. Then `cookie_dialog::install_inputs` with that jar and the store.
- Saves after each completed send (the Console notification hook), chained and merged; none before the first load. A save failure is a `StartupProblems` entry.

## Decisions
- `TestServer` cannot emit `Set-Cookie`, so the tests seed the jar through `store_response_cookies`. The capture direction is pinned in `http_engine`'s `cookie_transport_tests`.
- Loaded rows replace cookies captured before the load lands. The jar has no merge API, and the store opens at startup, before any send.

## Deferred (LOW, filed)
- The Manage Cookies dialog's own `save_jar` (`response_viewer/src/cookie_dialog.rs:421`) is not on the save chain, so its writes can still race send-triggered saves.
- A pending first load from an earlier `init_with_store` can set `load_finished` for a newer jar (test-only path; the binary initialises once).
- Saves run on every `ConsoleStore` change, not only completed sends; merged, but still a full rewrite per burst.
