## What shipped
Layered settings: embedded `assets/settings/default.json` merged with the user's `settings.json`
(through a `paths` helper for the platform config dir). Typed `Settings`, a `SettingsError`, and a
GPUI Global store behind a `register`/`get_global` trait. Reload on change via a background poll
watcher; a malformed user file reports an error and **keeps the last good values**.

## Findings history — the step was too big for one dispatch
The step's Goal named six distinct mechanisms (paths helper, GPUI Global, typed trait, embedded
defaults, merge layer, background watcher, error recovery). Dispatched as one run it failed **three
times** — an empty reply, a provider content-filter block, then another empty reply — despite a
short, plain brief. Split into three chunks (types+defaults → GPUI store+trait → watcher+recovery),
each small enough to build, verify and commit alone. **All three passed first try.**

The review confirmed the combined result and filed 2 LOW: the watcher path has zero test coverage
(the step's own test list is exactly the 4 named tests, so the gap is structural), and
`record_error` notifies observers on every 500 ms poll even when the error is unchanged.

## Learnings
- **A step whose Goal names 6+ distinct mechanisms is a multi-run step.** Split it before blaming
  the transport. This one cost three failed dispatches to learn.
- A short brief does not rescue an oversized scope. The filter denial and the empty replies were
  both downstream of one run being asked to do too much.
- A structural test gap can be the step's own fault, not the implementer's: when the step pins
  `PASS 4` and names 4 tests, there is no room to cover the 5th mechanism.

## Deferred
Issues #15 (watcher test coverage) and #16 (notify-on-unchanged-error). Both are LOW and both need
a follow-up that either adds coverage or extends the harness so `PASS` counts more than the named
